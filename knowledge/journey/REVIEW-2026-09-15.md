## 00. Pre-send checklist

### What is already right

**Quiet hours are exact.** The doc says 8 AM to 8 PM PT transactional, 9 AM to
8 PM PT bulk. `email/config.yaml` has `send_hour_start_pt: 8` /
`send_hour_end_pt: 20`; `ops/messenger/config.yml` has `send_window_start: 9` /
`send_window_end: 20`. Match. Sign as is.

**The 14-day thread window is exact.** Item 1 says 14 days;
`presend.thread_window_days: 14`. Match.

**Items 1, 2, 5 and 6 have working code.** `presend.check()` implements
opt-out, quiet hours, the line rule, cross-line threads, the inbox, open
scheduling tickets, frequency, standing go and the STOP line. This is not a
paper checklist.

### What has to be fixed before it is signed

**A. Item 3 contradicts itself, and the contradiction is live.**
The doc: "A standing go is one written in `email/config.yaml`
(`presend.standing_go`) for a stage that is REVIEWED." No stage is REVIEWED.
But `standing_go: [po_welcome, low_balance_family]` exists today, and
low_balance is armed and texting families about money. So by this checklist's
own definition, two live purposes are running on an invalid standing go.
**Decide:** either standing go does not require a REVIEWED stage (say so), or
those two are grandfathered by name and date (say that), or they pause until 00
and 01 are signed. Roman's call, and it is the one item that cannot be deferred.

**B. Item 2's line rule does not match the code.**
The doc asks "Any deal at Pre-Lesson **or later** in the current season?"
`presend._audience()` asks only whether **any** deal was created since
`season_start` (2026-08-15), at **any** stage. A family with a brand-new deal
sitting before Pre-Lesson gets the support line from the code and the
charter_sales line from the doc. This decides which number texts a family, so
it cannot stay ambiguous. **Recommend** the code's rule (any deal this season =
scheduling owns them) because it is simpler and fails safe toward the line the
family is already on; then fix the doc to say that.

**C. Item 5's frequency rule does not match the code.**
The doc: "FAIL: the count is 1 or more and this is a new touch", and "the
transactional SMS engine enforces one text per family per 24 hours."
The config: `max_sms_per_day: 2`, `min_gap_hours: 20`. The code holds on the
*second* text, and on a gap under 20 hours. So the code permits exactly the
thing the doc calls a fail. **Recommend** the doc's stricter rule for new
touches (`max_sms_per_day: 1`), since item 5 exists because of three texts in
an hour. Either way, one number.

**D. Item 1 names six sources; the code can read three.**
Checked by code: JustCall on every line, the HubSpot conversations inbox, open
tickets. **Not checked by any code:** danielle@ and paola@ sequences, the
charter@ mailbox, and Gmail sent (item 5 names it too). A human passing this
checklist does six lookups; an agent does three and cannot know what it missed.
**Fix:** mark the three unreadable sources "human only, no code" in the file,
the way the template asks gaps to be written. Then `agent_readable: true` means
something honest.

**E. Item 4 has no code at all.**
There is nothing in `presend.py` about tutor availability or who named a tutor.
It is a human check. Say so in the file.

**F. Item 6 omits the STOP-line exemptions.**
The doc states the rule absolutely. The config exempts five purposes:
`po_welcome, po_push, tor_confirm, tor_email_ask, tutor_ask`. Either the doc
lists them and says why, or the exemptions go.

| **Acknowledgement** — a receipt, identical for everyone, "we got it, here is the calendar" | No | **Agent alone** |
| **First touch opener** — personalised, asks for their time, reads their situation | Yes | **Draft**, as written today |

**Proposed amendment to the "may do alone" line:**

> **Alone:** classify; create the ticket with the routing table's owner and
> SLA; stamp an `[Agent]` note; log the call; stamp the lead status the call
> ladder allows; **send the acknowledgement (receipt + booking link) on the

> **Draft:** any message that reads the family's situation back to them, names

the argument for keeping the opener at draft is already on the record: the
